# 设计说明：本地分片复制键值存储

本系统是一个**完全本地、离线可复现**的分片复制键值存储教学实现：不依赖任何外部服务、
真实凭据或付费组件。副本间的"网络"是一个可注入故障的内存组件，可精确控制节点崩溃、
网络分区与恢复，从而在单进程内确定性地演示一致性、容错切换与幂等规则。

## 1. 总体结构

```
client.go        带请求标识与自动重试的客户端
cluster.go       集群编排：路由、副本装配、Transport、故障编排、客户端读写入口
shard.go         分片区间路由与多数派计算
node.go          副本节点：Raft 风格的选举、日志复制、提交、强/最终读
log.go           持久日志（JSON-lines，追加 fsync；崩溃后重载）
machine.go       顺序应用日志的键值状态机（含请求级幂等与 CAS）
network.go       故障注入网络：崩溃 / 断链 / 隔离 / 恢复 / 可达判定
errors.go        可区分的失败原因码
cmd/demo/        离线演示程序
```

数据模型：

- 集群划分为若干**分片**，每个分片负责一个左闭右开 `[Start, End)` 的键区间；
  各分片区间必须首尾相接、不重叠（末片 `End=""` 表示无上界）。
- 每个分片有**奇数个**副本（默认演示 3 副本，容忍 1 个故障，多数派 = 2）。
- 每个副本持有一份**持久日志**（`term/index` 编序）与一个按日志顺序应用的**状态机**。

## 2. 一致性语义

### 2.1 写入（多数派提交）

1. 客户端请求只能发给分片**主副本（leader）**；打到非主会得到 `NotLeader`（附带主提示）。
2. 主把操作追加到本地日志后，通过 `AppendEntries` 并发复制给 follower。
3. 当一条**当前任期**的日志在**多数派**副本落盘后，主推进 `commitIndex` 并应用到状态机，
   此后才向客户端返回成功。遵循 Raft 安全约束：旧任期条目不能被"直接"提交，
   只能随其后一条当前任期条目被间接提交。
4. 因此：**一旦返回成功，该写入已在多数派持久化，后续任何主切换都不会丢失或回滚它。**

主在追加前还会做一次"可达多数派预检"：连多数派都凑不出来时立即返回 `NoQuorum`，
避免请求悬挂；等待确认期间若掉到少数派，也会以 `NoQuorum` / `NoShardLeader` 结束。

### 2.2 读：两种语义

- **强一致读（ReadStrong）**：只在主上执行，且读前先向多数派发一轮心跳确认
  "我仍是主且与多数派连通"（ReadIndex/租约式确认的简化版），然后读本地已提交状态。
  旧主（被分区、任期已过期）或凑不齐多数派时，读请求被拒绝而**不会返回可能过期的值**。
- **最终一致读（ReadEventual）**：在任一存活副本上读其**本地已应用**状态。
  它可能落后于主，但读到的永远是"曾经被多数派提交过"的数据，绝不会读到未提交数据。
  当分片所有副本都崩溃时才以 `ReplicasUnavailable` 拒绝。

### 2.3 版本与 CAS

- 每个键有单调递增的 `Version`；每次成功的 `put`/`delete` 都使版本 +1。
- 删除写**墓碑（tombstone）**：读返回 `KeyNotFound`，但版本号继续递增、不回滚。
- 写请求可携带 `ExpectedVersion`：与当前版本不一致时返回 `CasConflict` 且**不改动数据、
  不占版本号**。并发写因此不会静默互相覆盖。

## 3. 故障切换（Leader 选举）

采用带 **Pre-Vote（预投票）** 的 Raft 风格选举：

- follower/candidate 在一个**随机选举超时**（`[base, 3*base)`，加密随机源抖动）内
  收不到主心跳就发起选举；主周期（约为超时的 1/4）发心跳。
- **预投票阶段**不递增任期、不持久化、不改 `votedFor`：候选者先以 `term+1` 探测
  自己能否拿到多数派，只有预投票通过才进入正式选举。这避免了"分区中的节点反复
  抬高任期扰乱现任主"，也避免被崩溃旧主的残留选票锁死。
- **同一预任期单站队**：一个节点在同一预任期只会支持一个候选者；同意他人的预投票后
  会推迟自己的选举时钟、本预任期内不再自我提名。配合随机超时，先到的候选者稳定获得
  先发优势，消除瓜分选票活锁。
- 投票依据"日志是否足够新"（先比末条任期，再比末条下标），保证当选者拥有所有已提交日志。
- 持久化 `currentTerm`；节点见到更高任期立即退回 follower，因此**旧主恢复后不可能
  用旧任期重新当选，也不可能覆盖新主已提交的数据**。

切换规则与降级红线：

- 剩余副本**仍能形成多数派** → 自动选出新主继续读写，已提交数据不丢。
- 存活/可达副本**不足多数派** → 明确拒绝写入（`NoQuorum` / `NoShardLeader`），
  **绝不降级**为单副本可写；强一致读同样被拒，最终一致读在存活副本上仍可服务。
- 被隔离在少数派的旧主：其写在"可达多数派预检"或等待确认阶段即被拒；
  分区愈合后它以 follower 身份通过日志复制追赶收敛。

## 4. 幂等、重复提交与离线追赶

- 每个写请求可携带客户端生成的**请求标识（RequestID）**。状态机在按日志应用时维护
  "请求标识 → 首次结果"映射（该映射随持久日志重放而重建）。
- **同一请求标识永远只生效一次**：重复提交（含"主已提交但响应丢失后重试"、
  以及并发重复提交）直接返回首次结果，版本与值都不再改变。客户端在整条重试链上
  复用同一标识，这是不重复生效的关键。
- 版本冲突（CAS）同样在应用时按日志顺序串行判定，冲突结果也会被幂等记住。
- 离线/落后副本恢复后，主依据各自的 `nextIndex/matchIndex` 通过 `AppendEntries`
  补齐缺失日志；遇到冲突任期会在不一致处截断本地后缀后续接（绝不截断已提交前缀），
  最终所有副本与已提交状态收敛一致。长时间离线（落后很多条）也能追平。

## 5. 持久化与崩溃恢复

- 日志以 JSON-lines 追加写文件，每次追加 `fsync`；`currentTerm` 单独原子落盘。
- 崩溃（`CrashNode`）模拟进程退出：停止响应、保留磁盘；恢复（`RestartNode`）等价于
  全新进程：重载日志与持久任期、重放状态机（含幂等结果表），再以 follower 身份加入。
- 全新进程启动会清空上一进程残留的 `votedFor`（该意向随旧进程死亡而失效），
  避免"全体同时重启"时被死票平白锁住首轮选举；持久 `currentTerm` 已足以保证
  旧主不会用旧任期当选。
- 以 `dataDir=""` 构造时为纯内存模式（用于不需要跨重启持久化的用例）；
  需要验证崩溃恢复的用例使用临时目录 `t.TempDir()`。

## 6. 可区分的失败原因码

错误统一为 `*StoreError`，用 `store.ErrorCode(err)` 取码：

| 原因码 | 含义 |
| --- | --- |
| `KeyOutOfRange` | 键不属于所请求的分片 |
| `KeyNotFound` | 键不存在或已删除（业务结果，区别于不可用） |
| `NotLeader` | 请求打到非主副本（消息中带当前主提示） |
| `NoShardLeader` | 分片当前无已确认主（通常正在选举或凑不齐多数派） |
| `NoQuorum` | 存活/可达副本不足多数派，写或强一致读被拒 |
| `ReadModeConflict` | 强一致读打到非主/旧主，或读期间领导权丢失 |
| `ReplicasUnavailable` | 最终一致读时该分片已无任何存活副本；或配置副本数非法 |
| `CasConflict` | 乐观版本检查失败，未做任何修改 |
| `ShardUnavailable` | 分片不存在/不可用 |
| `Unavailable` | 节点崩溃、RPC 不可达、客户端上下文超时等 |

单测与演示日志会打印每次拒绝/选主/投票的**判定依据**（存活数、多数派阈值、投票明细、
冲突下标/任期等），失败时可直接定位被破坏的是哪条不变量。

## 7. 已知边界（教学实现的简化）

- 所有副本跑在**同一进程**内，"网络"是同步内存调用 + 故障注入；没有真实 socket、
  磁盘页缓存或时钟漂移问题，也不模拟消息乱序/重复/拜占庭故障。
- 日志为单文件 JSON-lines、无日志压缩（snapshot）与分段，规模大时重放会变慢；
  状态机的请求标识表随日志增长、无 GC。
- 成员变更是静态的（启动时固定副本集），不支持运行中增删副本、再均衡或分片迁移。
- 强一致读用"一轮多数派心跳确认"实现，而非完整 ReadIndex 消息；在极小时间窗内
  语义等价于租约确认，但未做时钟假设的形式化证明。
- 选举超时是面向本地快速演示调小的（数百毫秒）；真实部署应按 RTT 重新标定。
- 无鉴权/多租户/跨分片事务；跨分片操作不提供原子性。
