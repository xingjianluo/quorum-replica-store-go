# 本地分片复制键值存储

这是一个只依赖 Go 标准库、可完全离线运行的进程内分片复制键值存储。项目用确定性的本地故障注入模拟副本崩溃、网络分区和恢复，目标是让分片路由、多数派写入、主副本切换、副本追赶、客户端重试、无人值守自动接管、整套重启恢复和在线扩容在故障前后都产生一致且可解释的结论。

> 当前实现是教学与可验证性优先的库，不是生产网络服务；没有真实 RPC，网络是进程内的可达性模型。默认纯内存构造仍不写磁盘；只有显式提供本地数据目录时才开启持久化（见第 10 节）。崩溃是测试可控的逻辑故障，副本的内存日志和键值状态会保留，用于模拟“进程停止但持久日志仍在”的副本。自本次迭代起，每个副本集内置一个可配置节拍的后台探活/选举循环，无需任何客户端请求即可完成主副本接管。

## 2. 分片与副本配置

分片区间采用字符串字典序的半开区间：

- `Start == ""`：从最小键开始。
- `End == ""`：到最大键结束。
- `key` 属于某分片当且仅当 `Start <= key < End`。
- 所有分片必须首尾相接，完整覆盖键空间，不能有缺口或重叠。

每个分片至少配置 2 个副本。多数派为：

```text
quorum = floor(replica_count / 2) + 1
```

例如 3 副本需要 2 个确认，5 副本需要 3 个确认。2 副本也需要 2 个确认，因此任意一个副本失效都不能继续写入。

示例：

```go
store, err := quorum.NewStore([]quorum.ShardSpec{
    {
        ID:    "low",
        Range: quorum.ShardRange{Start: "", End: "m"},
        ReplicaIDs: []string{"l1", "l2", "l3"},
    },
    {
        ID:    "high",
        Range: quorum.ShardRange{Start: "m", End: ""},
        ReplicaIDs: []string{"h1", "h2", "h3"},
    },
})
```

`"l"` 属于 `low`，`"m"` 属于 `high`。

## 3. 一致性语义

### 3.1 写入

写入必须携带非空 `RequestID`。主副本把写入追加到自己的日志后，复制给当前可达副本；只有收到包括自己在内的多数派确认，才推进提交点并物化键值。

返回结果包含：

- `Version`：该键的新版本号，从 1 开始递增。
- `CommitIndex` / `CommitTerm`：提交位置和主副本任期。
- `LeaderID`：服务本次写入的主副本。
- `Duplicate`：是否命中了已提交的相同请求。

可选 `CompareVersion` 实现 compare-and-swap：

- `CompareVersion == nil`：普通覆盖写，但仍产生新版本。
- `CompareVersion != nil`：只有当前版本等于该值才提交。
- 版本不匹配返回 `version_conflict`，不会静默覆盖。

### 3.2 强一致读

`ReadModeStrong` 必须通过当前主副本服务。服务前会确认：

1. 存活副本数至少为多数派。
2. 当前主副本仍能联系多数派。
3. 可达副本中不存在更高任期。
4. 如没有合法主副本，会先尝试在可达多数派中选主。

强读返回的 `Stale` 恒为 `false`。若不能证明主副本有效，则拒绝，不会从少数派猜测结果。

`MinIndex` 可要求读取的提交点至少达到某个日志位置；达不到时返回 `strong_read_unsafe`。

### 3.3 最终一致读

`ReadModeEventual` 可通过 `ReplicaID` 指定任意存活副本读取。它允许读到旧数据，因此：

- 响应中的 `Stale=true` 表示该副本落后于其他存活副本，或它无法联系多数派、无法证明自己不旧。
- 少数派副本仍可执行最终读，但一定会被标记为可能旧。
- 最终读不能指定 `MinIndex`，因为这种读模式不承诺读法定人数。

## 4. 主副本切换

选主规则采用 Raft 风格的任期、投票和日志新旧判断：

1. 候选人只能统计自己可达的副本。
2. 候选人和投票者都必须存活且未被注入网络分区。
3. 候选人日志至少与投票者一样新：先比较最后一条日志任期，再比较日志长度。
4. 得到多数派投票才能成为主。
5. 新主上任后先复制一条当前任期的 admin no-op 并提交，再处理用户写入。
6. 达不到多数派时不会产生新主，写入和强读必须拒绝。

旧主恢复或分区愈合后：

- `CatchUp` 只把当前主的已提交前缀复制给落后副本。
- 旧主未提交的旧尾项会被截断，不会覆盖新主任期内的已提交数据。
- 追赶不会把当前新主替换成旧主。
- 若某副本本地任期高于当前主，系统不会强行把它降级，而是要求重新选主。

普通写入、强读或显式 `ElectLeader` 都会在需要时触发选主。最终读不触发选主。

### 4.1 无人请求时的自动接管

从本次迭代起，每个副本集在构造后自带一个后台探活/选举循环（默认每 25ms 一个心跳周期，连续 200ms 无法确认主副本有效就自动重新选举）。判定依据：

- 在任主副本存活、且能联系投票多数派、且可达副本中没有更高任期时，刷新“最后确认时间”，主保持不变。
- 主进程崩溃、被分区到少数派，或出现更高任期时，**立即**把主记录置空，不再对外宣称它在服务。
- 超过选举超时仍无有效主，且存活投票成员能凑成多数派时，后台自动选出日志最新的新主，并先提交一条当前任期 no-op。
- 存活成员凑不出多数派时，系统停在无主、不可写状态；后台不会反复进行注定失败的选举，也不会让任何写入降级通过。

因此主副本失联后的接管时间在秒级以下、有明确上界（默认 200ms，可用选项覆盖），且全程不需要任何客户端读写。

可通过只读、无副作用的 `Leadership()` 如实查询当前状态：

```go
status := shard.Leadership()
status.LeaderID        // 当前主；没有合法主时为空
status.Writable        // 是否存在经多数派确认、任期最新的主
status.Reason          // 不可写时的稳定原因（见下）
status.VoterCount      // 当前投票成员数（不含追赶中的学习者）
status.AliveVoters     // 存活投票成员数
status.Quorum          // 当前多数派门槛
status.LeaderReachable // 在任主当前可达的投票成员数
store.Leadership()     // map[分片ID]LeaderStatus，一次查全部
```

`Reason` 的含义：`quorum_unavailable`（存活投票成员凑不齐多数派）、`no_leader`（当前无主）、`not_leader`（主已崩溃或被更高任期取代）、`strong_read_unsafe`（主存活但被分区、联系不到投票多数派）。即使旧主仍存活，只要它无法证明多数派，`Writable` 就为 `false`，系统不会把它当作在服务的主。

节拍可在构造期覆盖，也可以显式关闭自动接管（回到“只在请求到来时选主”的旧行为）：

```go
store, _ := quorum.NewStoreWithOptions(specs,
    quorum.WithFailoverTiming(50*time.Millisecond, 400*time.Millisecond, true))
// 第三个参数传 false 即关闭后台自动接管。
```

## 5. 幂等与离线副本追赶

### 请求标识

`RequestID` 的作用域是单个分片。同一个 `RequestID`：

- 相同 `Key`、`Value`、`CompareVersion` 的重复提交返回第一次提交的版本、索引和任期，`Duplicate=true`，不会重复产生版本。
- 相同 ID 但键、值或比较版本不同，返回 `duplicate_conflict`。
- 重试中的 CAS 版本不匹配返回 `version_conflict`，不会覆盖当前值。

客户端只重试以下可能恢复的错误（均配合同一请求标识，因此重试天然幂等）：

- `quorum_unavailable`
- `no_leader`
- `not_leader`
- `durability_failed`（写入可能已提交但多数派落盘未能确认；重试会先命中去重结果，不会重复生效）
- 强读的 `strong_read_unsafe`

以下确定性错误不重试：

- 键区间错误
- 非法读模式
- 缺少请求标识
- CAS 冲突
- 同请求标识但参数不同
- 参数非法

### 离线追赶

副本长时间离线期间，多数派可以继续提交多个版本。副本恢复后调用 `CatchUp`：

1. 确认当前仍有存活多数派。
2. 必要时重新选主。
3. 将当前主的完整已提交日志前缀复制给离线副本。
4. 离线副本一次性应用缺失的已提交条目，并重建键值和请求标识结果。
5. 未提交尾项不会被发布，也不会回滚已提交状态。

## 6. 本地故障注入 API

这些方法只在本进程内改变可达性和存活状态，不依赖网络或外部服务：

```go
shard, _ := store.Shard("users")

shard.CrashReplica("r1")
shard.RecoverReplica("r1")

shard.AddPartition("r1", "r2")    // 注入 r1/r2 之间的无向断边
shard.RemovePartition("r1", "r2")
shard.HealPartitions()

shard.CatchUp()                   // 恢复已提交前缀
shard.ElectLeader("")             // 显式触发选主
shard.Status()                    // 查看任期、存活、提交点和日志长度
shard.Leadership()                // 只读：当前主、能否写、不能写的原因
store.ExpandShard("users", []string{"u4", "u5"}) // 不中断读写在线扩容
store.Close()                     // 停止后台循环（持久化模式下最后 flush 一次）
```

分区模型是“无向断边”。复杂拓扑需要显式添加所有相关断边；注入不会自动推导多跳不可达。

## 6.1 整套实例停掉后再拉起（本地持久化）

默认构造 `NewStore` 仍是纯内存的；只有用 `NewStoreWithOptions` 提供本地数据目录时才开启持久化。完全离线，只写本地文件：

```go
store, err := quorum.NewStoreWithOptions(specs, quorum.WithDataDirectory("/tmp/quorum-data"))
// ... 对外提供读写 ...
_ = store.Close() // 停止后台循环并做最后一次整盘 flush（幂等）

// 之后任意时刻、甚至新进程里，用同一目录拉起：
restored, err := quorum.RestartStore(specs, "/tmp/quorum-data")
```

每个副本一个镜像文件 `<目录>/<分片>/<副本>.json`，采用“临时文件 + rename”原子发布。落盘内容与恢复不变量：

- 镜像只包含**已提交日志前缀**（`len(log) == commitIndex`）、由这些条目物化的键值状态、请求标识去重结果，以及 Raft 硬状态（`currentTerm`、`votedFor`）。
- 一条日志条目只有在**包括主在内的投票多数派都把新提交点落盘**后，才会对外返回成功；因此已确认写入在任意整停/硬杀后都还在。
- 只在少数副本上短暂出现、从未对外确认的写入，重启后不可能被当成已提交数据放出（未提交尾项在恢复时根本不存在）。
- 重启后每个键的版本号按已提交历史继续向上，不回退、不跳号、不出现重复版本；CAS 的比较版本也按历史判定。
- 请求标识去重结果随已提交日志恢复；同一请求在重启后再提一次仍是“命中已有结果”（`Duplicate=true`），不会再生效一遍。同 ID 不同参数仍返回 `duplicate_conflict`。
- 硬状态恢复保证同一任期内不会重复投票，避免重启后两个多数派各自选出主。
- 重启语义：所有副本视为重新存活（全新进程）、注入的分区全部清空、原领导身份作废；后台循环在选举超时内重新选出主，随后系统重新可读可写。个别落后副本可由下一次写入或 `CatchUp()` 追赶。
- 重启时所有副本都按“跟随者”启动，领导力必须重新赢得，不会凭旧的本地角色自称主。

新加入的扩容副本也会从磁盘被重新发现：成员身份由“日志最长副本”的已提交配置条目按序重放得到（详见 6.2）。扩容配置条目未提交就整停的，重启后停在上一次已提交的配置。

## 6.2 在线扩容副本数（不中断读写）

在不停止服务的前提下，可以把某个分片的副本数扩上去，例如从 3 副本扩到 5 副本：

```go
// 逐个加入；内部按“每次只加一个投票成员”执行。
if err := store.ExpandShard("users", []string{"u4", "u5"}); err != nil { ... }
// 或直接对副本集操作：shard.ExpandReplicaSet([]string{"u4", "u5"})
```

每个新副本的加入过程：

1. 先以**学习者**身份挂到主上：会被复制和追赶，但不投票、不计入多数派、不能当选。
2. 从当前主同步完整**已提交前缀**，绝不带空日志或落后日志取得投票权。
3. 追加一条成员变更日志条目（`ConfigChange`），按**旧配置多数派**复制并提交；提交点同样要多数派落盘。
4. 配置条目提交并落盘后，学习者原子转为正式投票成员。从这一刻起，后续每一条写入立即使用新的多数派门槛。

安全性依据是“一次只加一个投票成员”：旧配置 `C` 与新配置 `C+1` 的任意两个多数派必有交集（3→4：2/3 与 3/4；4→5：3/4 与 3/5），因此扩容期间不可能出现两拨副本各自凑够多数派、各自提交冲突结果。成员变更本身走普通日志和多数派提交，所以已提交数据不丢、请求不重复生效、版本不冲突不回退；扩容完成后新副本与已提交状态完全一致。

- 扩容需要当前主和旧配置多数派可用；中途故障导致配置条目没提交时，新节点回滚为“未加入”，系统维持旧配置，可在多数派恢复后重试。
- 当前只支持**增加**副本、且每次一批内部串行单节点加入；不支持缩容（删除副本）。一次跳过多于一个成员的变更是两次独立的单节点变更。
- 扩容期间不可并发调用第二次 `ExpandShard`（副本集内部串行，但成员变更是显式 API，应由调用方避免重入）。


## 7. 错误分类

错误可通过 `errors.As` 转成 `*quorum.Error`，读取稳定的 `Kind`：

| Kind | 含义 |
| --- | --- |
| `invalid_config` | 分片区间、副本数量或 ID 配置非法 |
| `key_out_of_range` | 键不属于被寻址分片，或没有分片拥有该键 |
| `no_shard` | 指定的分片不存在 |
| `no_replica` | 指定的副本不存在 |
| `quorum_unavailable` | 存活或可达副本不足多数派，不能写入或强确认 |
| `no_leader` | 当前没有主副本，且操作需要主副本 |
| `not_leader` | 假定主副本已被更高任期取代 |
| `replica_unavailable` | 指定副本已崩溃，或故障状态转换非法 |
| `version_conflict` | CAS 比较版本与当前版本不同，或日志追赶发现已提交冲突 |
| `duplicate_conflict` | 同一请求标识已用不同参数提交 |
| `missing_request_id` | 写入缺少用于安全重试的请求标识 |
| `invalid_read_mode` | 读模式非法，或读模式与 `ReplicaID` / `MinIndex` 组合冲突 |
| `strong_read_unsafe` | 无法证明强读或最低提交点要求安全 |
| `invalid_argument` | 空键等通用参数错误 |
| `durability_failed` | 本地镜像写入失败，或投票多数派未能把新提交点落盘（写入不会对外确认） |
| `config_change_rejected` | 成员变更非法（副本已存在、ID 为空、新副本无法在加入前追平已提交前缀等） |
| `closed` | 实例已关闭后仍被调用 |

## 8. 本地验证

所有命令都不需要外部服务、凭据或网络：

```bash
go test ./...
go test -v ./...
go test -race ./...
go vet ./...
```

重点场景：

```bash
# 初始多数派写入、强读、最终读、重复请求
go test -v -run TestSmokeWriteStrongReadAndDuplicate ./...

# 主副本崩溃、剩余多数派选新主、旧主恢复追赶
go test -v -run TestLeaderCrashElectionAndOldLeaderCatchUp ./...

# 网络分区、多数派继续服务、愈合后收敛
go test -v -run TestNetworkPartitionElectsMajorityLeaderAndConvergesAfterHeal ./...

# 多数派边界：3/5 可服务，2/5 拒绝，恢复后继续
go test -v -run TestFiveReplicaQuorumBoundary ./...

# 客户端同一请求标识重试，不重复生效
go test -v -run TestClientRetriesSameRequestIDUntilMajorityRestored ./...

# 并发读写与精确一次提交
go test -race -v -run TestConcurrent ./...

# 可区分拒绝原因
go test -v -run TestDistinguishableRejectionReasons ./...

# 无人请求时主崩溃自动接管、诊断原因、接管时间上界
go test -v -run 'TestAutoFailover|TestLeadership|TestElectionTimeout' ./...

# 整套重启：已提交数据/版本/请求标识保留，少数派写入不复活，CAS 版本连续
go test -v -run TestRestart ./...

# 自动接管后再整套重启，新任期提交也保留
go test -v -run TestFailoverThenRestart ./...

# 在线扩容 3->5 与并发写入交错、门槛即时生效、边界拒绝
go test -v -run 'TestOnlineExpansion|TestExpansion' ./...
```

测试使用 `t.Logf` 打印：

- 候选人、投票人、任期、日志新旧比较和票数。
- 可达副本数、多数派大小和拒绝原因。
- 哪条日志在哪个索引/任期提交，多少个投票副本把提交点落盘（`voterAcks`/`durableAcks`）。
- 副本恢复前后的提交点。
- 最终读是否可能旧。
- 后台心跳为何确认或失效主副本、超时多久后自动选出谁、为什么能/不能形成多数派。
- 扩容每一步：学习者何时挂上、何时追平、配置条目何时提交、新多数派是多少。
- 幂等判定究竟是“命中已有结果（DEDUP-HIT）”还是“新提交”。

测试失败时可直接根据日志判断破坏的是多数派、任期、日志匹配、提交点收敛、持久化多数派、成员配置交集、版本冲突还是请求标识幂等不变量。

## 9. 已知边界

- 默认 `NewStore` 仍是纯内存模式；只有显式 `WithDataDirectory` 才开启本地持久化。持久化是“每副本一个 JSON 镜像、提交时多数派落盘”，不是预写日志或 LSM，教学可读优先，吞吐和文件体积不在优化范围。
- 持久化只覆盖显式配置的数据目录；没有 fsync 策略调优、快照压缩、校验和或多盘冗余，也不处理目录被外部并发篡改。
- 重启模型假设整套本地实例一起重新拉起：所有副本重新存活、注入分区清空、原主身份作废后重新选举。它不模拟“部分进程持久盘损坏 / 磁盘内容不一致”的灾难场景。
- 后台心跳是进程内定时节拍（默认 25ms/200ms），不是真实 RPC 心跳；接管时间用墙上时钟度量，可通过选项调整，调度受 Go runtime 与机器负载影响，不提供硬实时保证。
- 没有真实网络、gRPC、HTTP、服务发现、认证或跨进程客户端。
- 操作在副本集内串行执行（一把互斥锁），重点是可解释和易测，不是高吞吐生产实现；后台循环与客户端请求共用同一把锁。
- 不提供删除、TTL、跨分片事务或二次索引。
- 请求标识去重结果会随已提交日志长期保存（含落盘镜像），没有垃圾回收。
- 成员变更只支持在线**增加**副本（内部单节点串行），不支持缩容、不支持一次跨多个成员的联合配置；扩缩容期间调用方不应重入扩容 API。
- 学习者是扩容过程中的临时内部角色，不通过对外 API 暴露；扩容失败回滚后，该副本 ID 需要重新通过扩容加入。
- 新副本以空状态加入并在取得投票权前被强制追平已提交前缀；当前没有“带历史镜像预热加入”的路径。
